一、测试概述
1.1 被测系统简介
被测系统为一款面向 A 股上市公司的「金融智能投研 Agent」Web 应用，采用 Streamlit 构建。系统核心能力包括：登录鉴权、在线自动取数（行情/多期财务指标/年报原文，巨潮、东方财富、新浪、腾讯四级数据源兜底）、规则引擎四维评分（盈利能力/成长性/偿债能力/现金流质量）、同业对标与四象限定位、年报 PDF 解析与 RAG 页码引用、一键生成 Markdown 研报、多轮追问对话、多公司对比、分析记录回看等。
1.2 测试范围与环境
本次测试使用 Playwright（Chromium 无头浏览器）自动化登录并遍历全部主要功能：登录/退出、单公司深度分析全流程（取数→结构化分析→五个结果页签→研报生成→追问）、多公司对比、使用说明、分析记录回看等。
浏览器：Chromium（Playwright，headless，1440×2600 视口）
主要测试标的：贵州茅台（600519）等热门股票
说明：测试账号为共享演示账号，部分数据（分析记录、当日用量）受其他并发用户影响，报告中已区分标注。
1.3 测试结论摘要
系统整体架构设计严谨（确定性规则引擎评分 + 大模型仅负责解读、四级数据源兜底、证据核对与 Agent 轨迹等），核心功能均可正常运行，评分结果可复现。但在 UI 呈现、异常处理、状态管理与安全细节上存在若干问题，其中「主题 CSS 以可见文本形式显示在页面上」与「取数接口偶发静默失败」问题对参赛评审体验影响较大，建议优先修复。具体问题与优化建议详见第三、四、五章。

3.2 问题详情与解决方案
B1（高）· 主题 CSS 代码以可见文本显示在页面上
问题描述：页面上方与下方各出现一段以「/* ===== v15 主题兜底层（变量驱动…）===== */」开头的 CSS 源码，以可见 <p> 文本形式直接渲染在页面正文中，而非被 <style> 标签包裹。
影响：首页与工作台均可见大段样式代码，严重破坏页面观感，直接影响参赛评审的第一印象。
根因分析：主题样式通过 st.markdown 注入时，CSS 字符串被作为普通 Markdown 文本渲染（未启用 unsafe_allow_html，或注入方式存在重复/转义问题），导致 <style> 内容泄漏为可见文本。
修复方案：
统一用 st.markdown("<style>…</style>", unsafe_allow_html=True) 注入主题样式，并确保 CSS 位于 <style> 标签内；
删除重复注入的 CSS 副本，仅在应用入口注入一次；
修复后回归验证：页面正文中不应再出现任何以 “/*” 开头的 CSS 文本。
B2（高）· 取数接口偶发静默失败
问题描述：在连续多次取数测试中，出现过一次「点击获取数据后，剩余额度不变、未出现“已获取”提示、“开始结构化分析”按钮始终保持禁用（disabled）」的现象，期间界面没有任何错误提示。
影响：用户无法区分“正在取数”与“取数失败”，核心流程被卡住却无任何引导，属于较严重的可用性缺陷。
根因分析：外部免费数据源（东方财富/新浪等）存在限流或网络抖动；当取数管道所有兜底源都失败或超时时，系统未把失败状态与原因回传给界面，导致按钮静默禁用。
修复方案：
取数失败/超时时显式抛出 st.error / st.warning，提示“取数失败，请稍后重试或检查网络”，并列出失败原因；
增加重试与指数退避（429 限流按 15s/30s/45s 退避重试），并加缓存与熔断；
“开始结构化分析”按钮禁用时，展示禁用原因提示（tooltip 或 caption）。
B3（中）· 研报生成后 UI 状态残留
问题描述：点击「研报」页签的“生成完整研报并在此查看”后，研报正文已正确生成，但“还没有研报。点下方按钮直接在这里生成…”的占位提示、生成按钮以及“正在生成完整研报……”的加载文案仍与正文同屏显示。
影响：页面状态混乱，用户难以判断研报是否已生成完成。
根因分析：研报生成的状态切换（None→生成中→已完成）未做完整的条件渲染，初始占位块与加载文案在生成完成后未清除/隐藏。
修复方案：
用单一状态变量（未生成/生成中/已完成）驱动研报区渲染，三种状态互斥；
生成完成后隐藏占位与按钮，仅保留研报正文与下载入口；
可选：将“生成完整研报”按钮在生成后置为已禁用或置灰。
B4（中）· 热门股票下拉选股后出现误导性告警
问题描述：从“热门股票”下拉框选择股票后直接点“获取数据”，界面先短暂出现“请先输入 6 位股票代码或公司名称，再点击获取数据”的告警，随后又提示“已获取 … 数据”成功。告警与结果相互矛盾。
影响：给用户造成“操作无效”的错觉，虽有成功提示但体验割裂。
根因分析：校验逻辑只检查了文本输入框是否为空，未考虑“热门股票下拉已选中”这一合法路径，产生误报。
修复方案：
将“下拉选股”与“手动输入代码”合并为统一的取数入参，任一合法即通过校验；
仅在两种输入都为空时才提示“请先选择或输入股票”。
B5（中）· 分析记录与“获取数据”耦合，易产生重复记录
问题描述：实测仅点击“获取数据”（未点击“开始结构化分析”）也会在“分析记录”中生成一条含“综合 8.4”的记录；同一只股票反复测试会累积多条内容几乎相同的记录（实测贵州茅台出现多条“综合 8.4”）。
影响：“分析记录”的语义被稀释，历史记录难以区分哪条是真正完成的分析。
根因分析：规则引擎在取数阶段即完成评分并落库记录，而“开始结构化分析”未复用/更新同一记录，导致记录与取数耦合、重复累积。
修复方案：
明确记录的唯一键（如 账号+股票代码+评分基准期），同键记录覆盖更新而非重复插入；
或将记录落库时机改为“开始结构化分析”完成之后，取数阶段仅做草稿。
B6（中）· 共享账号下会话隔离不足
问题描述：测试期间在“分析记录”中观察到他人（其他并发评测用户）对“山西汾酒、宝钢股份”等股票的分析记录，同一账号下所有会话的分析历史互相可见。
影响：演示账号多人共用时，历史记录互相污染，且存在轻微的信息泄露风险。
根因分析：分析记录按账号（而非按浏览器会话）持久化，缺少会话级隔离或命名空间区分。
修复方案：
为每个浏览器会话生成独立 session_id，记录按 session_id 隔离展示（或提供“仅看我的本次会话”开关）；
正式环境建议改为账号+会话双层隔离，并设置更短的过期时间。
B7（中）· 数据接口存在 HTTPS 降级 HTTP 明文连接
问题描述：取数过程中界面提示“本次取数中有 1 个接口由 HTTPS 降级为 HTTP（明文连接）”，说明部分数据源请求走明文传输。
影响：行情/财务数据经明文 HTTP 传输，存在被中间人截获篡改的风险，与金融数据的安全要求不符。
根因分析：部分免费数据源（新浪/腾讯等）仅提供 HTTP 端点，或网络环境拦截了 HTTPS。
修复方案：
优先使用 HTTPS 端点，对仅支持 HTTP 的源做服务端代理中转并统一走 HTTPS；
保留降级提示的同时，增加“禁止明文降级”的开关，默认关闭明文降级。
B8（低）· 登录页演示维度命名与实际评分不一致
问题描述：登录/落地页的“财务评分·四维”演示区显示维度为“盈利/成长/偿债/营运”，而实际结构化分析的四维为“盈利能力/成长性/偿债能力/现金流质量”。
影响：首页演示与真实输出口径不一致，易让评审误以为评分维度含“营运能力”。
修复方案：
统一首页演示区与真实引擎的四维命名；
首页演示数据建议标注“静态示例，非真实评分”以免误导。
B9（低）· 多公司对比页冗余告警
问题描述：多公司对比页在未取数时同时显示两条含义基本重复的告警：“以下公司选了在线取数但尚未成功取到数据…”与“以下公司的输入未完成…”。
修复方案：
合并为一条告警，分点列出原因与处理方式。
B10（低）· “向量化”用量计数增长异常偏快
问题描述：测试期间“今日用量·向量化”计数从个位数快速攀升至 167 批（含共享账号并发因素）。单次取数/分析触发的向量化批次偏多，存在重复向量化或批次划分过细的嫌疑。
影响：额度消耗过快，且可能带来不必要的 embedding 调用成本与延迟。
修复方案：
排查取数/分析链路中是否存在对同一文本的重复 embedding 调用；
对年报切分与向量化结果做持久化缓存（按文档+报告期+chunk 指纹去重），避免重复向量化。

四、优化建议（基于知识库调研）
结合对被测系统的实测问题，以及金融 RAG 投研、确定性评分、Streamlit 工程化等领域的最佳实践，提出以下优化建议。
4.1 检索增强（RAG）能力提升
混合检索：当前仅使用语义向量检索（ChromaDB + DashScope）。建议叠加 BM25 关键词召回 + 向量召回的双路混合检索，并引入重排（Rerank），显著提升对“营业收入/净利润”等精确数值类查询的命中率。
表格感知切分：财报表格密集，普通按段落切块会破坏表格语义。建议采用表格感知/结构化切分（参考业界“Stop chunking tables”、Docling、表格 Cell 级证据追溯等实践），避免数值与表头被切散。
页码/单元格级引用：将“见年报第 X 页”进一步细化到“表格/单元格级引用”，提升证据可信度（业界研究表明表格单元格级引用比段落级引用更受金融用户认可）。
年报索引默认自动构建：当前“页码引用未启用”是默认状态，证据卡显示“0/10 项可定位到年报原文”。建议在取数成功后默认自动建立年报索引（可异步/后台），让页码引用成为默认能力。
ChromaDB 调优：按需调整 HNSW 参数（M、ef_construction、ef_search）与 chunk_size/chunk_overlap，并保证每个 chunk 语义完整、携带位置元信息。
4.2 数据获取层健壮性
缓存：对股票行情/财务指标/年报解析结果使用 @st.cache_data 或服务端缓存，避免每次交互都重复请求外部接口（业界经验显示缓存可带来 3–5 倍性能提升）。
重试与熔断：为每个数据源加指数退避重试（429 限流）、超时控制与熔断器，并在所有源失败时显式报错。
全 HTTPS：消除 HTTP 明文降级，见 B7。
批处理向量化：对比/批量取数时合并 embedding 请求，避免逐条调用，降低额度与延迟。
4.3 性能与体验优化
减少 Streamlit 全量重跑：当前部分交互（如切换页签）可能触发重跑并重复取数/向量化，建议用表单提交、st.session_state 缓存与片段化（st.fragment）隔离副作用。
加载态与状态机：为“取数→分析→研报”建立清晰的状态机，消除占位/加载状态残留（对应 B2、B3）。
告警去重与文案统一：合并重复告警，统一首页与引擎的维度命名（对应 B8、B9）。
4.4 安全与合规
会话隔离：账号+会话双层隔离分析记录，避免共享账号互相污染（对应 B6）。
敏感信息与免责声明：登录页与研报已有“仅供参考，不构成投资建议”声明，建议在导出 Markdown 中同样保留；对取数内容做来源标识与脱敏。
审计与可追溯：当前 Agent 轨迹已较好，建议增加结构化日志（时间戳、步骤、耗时、失败原因）并支持导出，便于复盘。
4.5 可观测性与额度管理
额度透明化：在界面明确“每次取数/分析消耗多少额度”，并给出当日剩余与明细，避免用户对额度扣减产生疑问。
幻觉与数值核对增强：当前已有“证据核对/证据卡”，可进一步引入“原子断言级核验”（将结论拆成若干断言逐条与原文比对），对无法支撑的结论显式标注“证据不足”或拒答。
