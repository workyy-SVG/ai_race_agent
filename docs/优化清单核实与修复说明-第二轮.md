## 二、逐条判定与证据

### 🔴 1. 热门股票下拉框会"锁死"手动输入框 —— 真实存在，已修

**根因**（`app.py` 原 1603-1610 行）：

```python
if _code:                                     # _code = 下拉框选中的代码
    st.session_state[f"{key_prefix}_kw"] = _code   # 每次渲染都执行！
kw = st.text_input(..., key=f"{key_prefix}_kw")
```

只要下拉框停在某只股票上（非"手动输入"），**每一次 rerun** 都会把输入框写回那只股票。
评委改成别的代码后，任何一次交互（点按钮、切 Tab）都触发 rerun → 输入被覆盖。
用户视角就是"输入框改不动"。

**更严重的后果**：用户以为在查询自己输入的代码，取数却仍按下拉选中那家执行 ——
**这正是"输入错误代码，页面显示贵州茅台"的直接原因**（下拉框停在 600519 上）。

**修法**：记一个 `last_pick`，只在**下拉选择真的发生变化**时才回写输入框。

```python
if _code and st.session_state.get(_last_pick_key) != _choice:
    st.session_state[_kw_key] = _code
st.session_state[_last_pick_key] = _choice
```

### 🔴 2. 错误代码 → 显示上一家/别的公司数据（PDF P0-01）—— 真实存在，已修

三个环，全部实测过：

**环 A：搜索接口是模糊匹配，取 `hits[0]` 会拿到用户没输入过的公司**

直接调 `data_source.search_stock()` 实测（2026-10-15）：

| 输入 | 搜索结果 | 旧代码会取 |
|---|---|---|
| `00000`（5 位） | 10 条，首条 `000001 平安银行` | ❌ 平安银行 |
| `60051`（5 位） | 9 条，首条 `600510 黑牡丹` | ❌ 黑牡丹 |
| `abc` | 1 条 `180306 华夏安博仓储REIT` | ❌ 一只 REIT |
| `999999` | 0 条 | ✅ 报错 |

**环 B：取数失败时旧数据不清空**
`f"{prefix}_online"` 及 `_online_name/_code` **不在**清空列表里，而 `raw_data` 仍非空 →
`run_btn` 的 `disabled=not raw_data` 为 False → 分析照常可点，结论仍是上一家公司的。

**修法**：新增 `data_source.resolve_stock(keyword)`，原则是"**绝不猜**"：

- 全数字但不足 6 位 → 直接拒绝，连接口都不请求
- 6 位代码 → 必须**精确命中** `code == kw`；只命中"相近匹配"就拒绝并列出候选
- 纯英数非 6 位（如 `abc`）→ 拒绝（A 股简称必含中文）
- 名称 → 完全同名优先；唯一命中直接采用；**多命中交给用户在候选里确认**（radio + 确认按钮）
- 新增 `_panel_clear()`：任何失败/换标的路径都先清空该面板全部数据类键

**实测结果**：

```
'600519'  [OK    ] 600519  贵州茅台
'000858'  [OK    ] 000858  五粮液
'abc'     [REJECT] —— 既不是 6 位代码，也不像 A 股公司名称
'999999'  [REJECT] —— 未找到对应证券
'00000'   [REJECT] —— 应为 6 位数字
'60051'   [REJECT] —— 应为 6 位数字
'贵州茅台'  [OK    ] 600519  贵州茅台
'平安'     [AMBIG ] 8 个候选，等待用户确认
'贵州'     [AMBIG ] 9 个候选，等待用户确认
'京东方A'   [OK    ] 000725
'TCL科技'  [OK    ] 000100
```

**端到端验证（AppTest）**：已登录 → 输入 `999999` → 点「获取数据」→
页面只出现「未找到与「999999」对应的证券」，**无任何 success 提示、无旧数据残留**。

### 🟠 3. 银行/保险股四维评分缺一维 —— 真实存在，已修

**根因**（`scoring.py` 原 `_DIM_FINANCE`）：

```python
"现金流质量": [("ocf_to_revenue", 1.0)],   # 银行财报里几乎取不到这个口径
```

银行 → 该维度恒为"数据不足" → `total = 三维平均`。

**修法**：按"该行业真的拿得到的指标"重构四维，权重归一化自动吸收缺失项：

| 维度 | 指标（银行 / 保险各取所需） |
|---|---|
| 盈利能力 | ROE(加权) + 净息差 NIM |
| 成长性 | 营收同比 + 归母净利润同比 |
| 资产质量 | 不良率 + 拨备覆盖率 + 拨贷比 + 新业务价值率 |
| 资本充足 | 核心一级资本充足率 + 偿付能力充足率 |

新增 4 张判分表（`nim` / `loan_provision_ratio` / `solvency_ar` / `nbv_rate`），
并补了对应的中文名、单位、正则抽取与 LLM 抽取提示词。

**自检输出（`python scoring.py`）**：

```
demo_bank  （ROE 14 / 不良 0.95 / 资本充足 13 / 拨备 420）
   盈利能力 9.8 | 成长性 4.2 | 资产质量 9.5 | 资本充足 9.0 | 总分 8.1   ← 四维齐全
demo_insurer（ROE 12 / 偿付能力 210 / 新业务价值率 24）
   盈利能力 9.3 | 成长性 6.6 | 资产质量 6.7 | 资本充足 7.4 | 总分 7.5   ← 四维齐全
```

自检里加了断言：银行/保险样例**不得出现任何 `None` 维度**，防回归。
UI 的评分卡片也改成按 `scores` 实际键动态渲染（原来写死四个维度名，金融口径会漏卡片）。

### 🟡 4. 双公司对比共用同一套行业框架 —— 部分成立，已修

**核实结果**：拆开看两半 ——

- **规则评分那一半本来是对的**：`_cmp_side_metrics()` 里 `_ind = ds.guess_industry(name) or industry`，
  两家各按自己的行业评分。评审说的"评分基准只套一个行业"在这条不成立。
- **提示词那一半确实错了**：`llm_stream([{... system_prompt_with_kb() ...}])` 用的是全局
  `industry`，所以模型收到的行业知识库只有一份。茅台(消费) 比 宁德时代(新能源) 时，
  新能源那一侧等于没有行业背景。

**修法**：`system_prompt_with_kb(industry_override)` 支持指定行业；对比时分别注入两家行业，
并在 prompt 里显式声明"两家分属不同行业，不可直接比高低"。

### 🟡 5. 东财字段口径靠硬编码"摸"出来 —— 属实，已加兜底

ds.sanity_check_metrics(metrics)   # 返回可疑项

### 🟡 6. 每日额度熔断云端不可靠 —— 属实，已文档化（不改架构）

核实：计数已从 `USAGE_FILE=/tmp/llm_usage.txt` 迁到 `budget.py`（原子写入 + 分桶），
但存储仍是容器本地文件 → **云端重启确实清零**。

**处置**：这是**接受的风险**，不是缺陷。理由写进了 `budget.py` 模块文档：

- 它是"防刷"的软熔断，不是计费依据（真实费用以服务商账单为准）
- 有登录口令挡在前面，陌生人刷不到
- 重启即清零 → 最坏情况是多花一档额度，**不会把应用锁死**

跨重启保留计数需要外部存储（Redis/DB/对象存储），2 天窗口内属过度工程。
**评审期的正确动作**：把 `DAILY_LLM_LIMIT` 调到 300，给评委留足测试余量。
需要自定持久化位置时设 `BUDGET_FILE=/path/to/counter.json`。
